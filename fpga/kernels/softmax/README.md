# Row softmax kernel (SmolVLA -12392 attention on the KR260)

Turns FP32 attention scores into probabilities for the int16 engine's P.V call. The output is `q` int16 in
[0, 32767] plus one FP32 scale per row, with `P = q * scale` and `scale = RN(1 / sum q)`. An FP32 output is a
compile-time option.

- One call is one 128-byte record in the float_top sequencer's record format (opcode `SOFTMAX` 0x40).
- A call covers B batch items of N rows x L keys.
- Ports: two read-only 128-bit ports (hp0, hp1) and the 128-bit `io` port. No new register, no new port.

**Status: verified on the host only.**

- The host build is bit-exact against the torch emulation in every case: 46 + 46 + 19 cases across three builds.
- csynth passes at 4.0 ns.
- Not run in Vivado, not run on the board.

## Arithmetic (exact definition: `smx_emu.py`)

Per row, with `c = fl32(p0 * fl32(log2 e))` and `p0` the score multiplier (1/8 for head dim 64):

1. **Mask.** `valid(n,k) = k < L` and, with `F_MASK`, `0 <= E[k] <= D[n]`.
2. **Row max.** Computed on FP32 total-order integer keys. No FP compare core.
3. **Fixed point.** `u = fix(max) - fix(x)`, where `fix(x) = x * 2^exp(c)` on a 48-bit Q.21 grid, truncated and saturating. `u` is clamped to 2^26.
4. **Exponent.** `t = u * Mc` in Q.37, where `Mc` is c's significand to 17 bits.
5. **2^-t.** One 1024-entry table (`T23 = 2^23 * 2^(-i/1024) * 32767/32768`) plus linear interpolation (13x13 multiply), then a shift by the integer part with rounding. The result is `ehi < 2^23`.
6. **int16 output.** `q = (ehi + 128) >> 8`, so q is in [0, 32767] and the max element is exactly 32767. The row scale is `RN(1 / sum q)`.
7. **FP32 output.** `p = fl32(ehi) * RN(1 / sum ehi)` (one IEEE multiply).
8. **Reciprocal.** `RN(1/S)` is the correctly rounded FP32 reciprocal of the exact integer sum. It comes from a normalised restoring divider (26 quotient bits plus a sticky bit), with two 1-bit units alternating rows, one row per 13 cycles.
9. **Fully masked rows.** Zero (`q = 0`, `scale = 0`, the sequencer contract), or uniform over the L keys with `F_EMPTY_UNIFORM` (torch's `softmax` of equal `finfo.min` scores).

Everything from the score bits to the scale bits is integer. So the host build is the hardware arithmetic, and
the hardware cannot differ by an FP core's last bit. Two IEEE single multiplies are the only exceptions, and they
are identical on both sides: `c` in `decode()`, and the FP32-mode output multiply.

## Interface

### Registers (standalone top = float_top's `s_axi_control` map, unchanged)

`w0` 0x18 (hp0), `w1` 0x24 (hp1), `w2`/`w3` (unused), `xmem` 0x48 (unused), `ymem` 0x54 (io), `M` 0x60, `K`
0x68, `N` 0x70, `AP_RETURN` 0x10.

- `M = 0x5F000040` selects SOFTMAX: `M[31:24]` = 0x5F kernel magic (the sequencer uses 0xA5), `M[7:0]` = 0x40.
- `K` = word index of the record (byte address >> 4) in w0's view.
- Pointer registers are 0, and every record address is absolute, as in the sequencer.
- Return value = status: 0 OK, 1 DIMS, 2 ALIGN, 3 OPCODE. On a non-zero status nothing is written.

In the sequencer, the dispatch calls `smx::decode(rec, p)` on the record it already fetched, then
`smx::softmax_core(w0, w1, ymem, p)`.

### Record (128 B, `fpga/kernels/sequencer/seq_format.h` field layout)

| field | content |
|---|---|
| f0 | `[7:0]` 0x40, `[15:8]` 0xC5, `[31:16]` flags: `F_QOUT` 0x0002 (int16 + scales; clear = FP32 rows), `F_MASK` 0x0100, `F_ENGINE` 0x1000 (engine layouts), `F_EMPTY_UNIFORM` 0x2000 |
| f3, f4, f5 | L = keys per row (1..256), N = rows per item, `[15:0]` B items (0 = 1) |
| slot A (f6..f8) | scores: byte address (40 bit), pitch (bytes, rows layout), item stride (bytes) |
| slot C (f12..f14) | output (q rows / FP32 rows / engine X section), pitch (rows layout), item stride |
| slot D (f15..f17) | row ranks D[n], int32, 4 per word (`F_MASK`); item stride 0 = shared by all items |
| slot E (f18..f20) | key ranks E[k], int32, 4 per word (`F_MASK`); item stride 0 = shared |
| slot F (f21..f23) | scales FP32, 4 per word (engine: the s_tok section); item stride |
| f24 | p0 = score multiplier (FP32 bits). The kernel uses `c = fl32(p0 * log2 e)` |

- Every address, pitch and stride must be a multiple of 16 bytes (else ALIGN).
- DIMS covers: L out of [1, 256]; a_pitch < ceil(L/4) words; c_pitch < ceil(L/8) (int16) or ceil(L/4) (FP32); a masked rows-layout call with N > 256; an engine call with pad32(N) > 256; engine without `F_QOUT`; FP32 requested in a build without `SMX_FP32_OUT`; c not a positive normal.
- Ranks must be below 32767. Internally E < 0 or E >= 0x7FFF is never visible, and D is clamped to [-1, 0x7FFE].
- Every SmolVLA mask is rank-representable, because the rows' visible key sets are nested. `ranks_from_mask()` builds the vectors, and `policy_check.py` checked all 1,584 masked calls of a chunk.

### DDR layouts (128-bit words, little-endian; FP32 lane j = bits [32j+31:32j], int16 lane j = bits [16j+15:16j])

**Rows layout** (default; the sequencer's "rows of A, q-out to C + F"):

- **Input.** Item b, row n starts at `A + b*strideA + n*pitchA`. Key k is in word k/4, lane k%4. Pad words and lanes are ignored.
- **int16 output.** Row n at `C + b*strideC + n*pitchC` holds 8 q per word, key k in word k/8, lane k%8. Keys >= L and pad words up to the pitch are written as 0.
- **Scales.** Row n's scale is at `F + b*strideF`, word n/4, lane n%4, contiguous over the item. The lanes after the last row of the item are 0, and `ceil(N/4)` words are written.
- **FP32 output.** Rows of 4 FP32 per word, pitchC.

**Engine layout** (`F_ENGINE`; `int16_linear.h` DRIVER CONTRACT; the attention kernel's Q K^T then P V chain):

- **Input.** The engine's Y tiling of one item: `Y[Mk/32][Np][32]` FP32, with `Mk = pad32(L)` (keys are the output channels) and `Np = pad32(N)` (rows are the tokens). Element (n, k) is at word `(k/32 * Np + n) * 8 + (k%32)/4`, lane k%4. The item is one contiguous burst of `Mk/32 * Np * 8` words.
- **Output.** The X section of the P V xmem image is `X[Np/32][L][32 rows]` int16: word `(n/32 * L + k) * 4 + (n%32)/8`, lane n%8. The s_tok section holds `Np` FP32. Rows n >= N get q = 0 and s_tok = 0.0, which the contract accepts as "any finite value".
- **Placement.** Point C at the image's X section and F at its s_tok section. The s_row section is attn_pack's.

## How it works (one DATAFLOW region; every loop pipelined at II = 1, all ports bursting)

| process | port | what |
|---|---|---|
| `pass1` | hp0 | rank tables (if `F_MASK`; once per call when their strides are 0), then each item as one burst in memory order: masks and the row max (4 lanes). Engine layout: per-row state between the Mk/32 groups in a 256 x 33 RAM |
| `pass2` | hp1 | the same words again: fix, 2^x, q, row sums (4 lanes; 2 table BRAMs). Engine: 256 x 84 row-state RAM |
| `recip` | | RN(1/S): 2 x 1-bit restoring dividers, 13 cycles per row |
| `shaper` | | rows: 8 q per word; engine: 32 x 32 transposes, 8 ping-pong LUTRAM banks |
| `writer` | io | data bursts (rows: per 256-row block; engine: one burst of 4*Kg words per tile), then the scales |

The scores are read twice, on two ports, instead of being buffered. This needs no row FIFO (no BRAM), and it
makes the engine layout possible at all: there a row's keys are spread over Mk/32 groups of the whole item, so
its max is known only at the item's last group.

## Time (cycles per element, ms per -12392 chunk at 250 MHz)

- **Throughput.** Each pass streams one 128-bit word per cycle, so 4 elements per cycle (0.25 cycles per element), with both passes in parallel on hp0 and hp1. The writer runs at 0.5 words per cycle (int16 out).
- **Short rows.** Rows shorter than 13 input words (L < 52) are paced by the divider at 13 cycles per row.
- **Lanes.** 4 lanes, not 16: the kernel is bound by one 128-bit read stream per pass, and 4 lanes already meet the time target. 16 lanes would need four ports per pass.
- **Fixed costs.** About 150 cycles per item (loop restart + DDR latency) and about 300 per call.

| LM prefix (16 layers) | 16 | (1, 15, 5, 81, 81) | 1.8 | 2.3 |

- **Assumption.** Both columns assume the DDR delivers two parallel 4 GB/s read streams plus about 1-2 GB/s of writes (7.6 GB/s read + 1.9 GB/s write at 35 ms). This is not measured on the board.
- **Not included.** The ARM's or sequencer's per-command overhead.

## Integration notes for float_top

- **Ports.** Uses w0 / hp0 (pass 1 reads and rank tables), w1 / hp1 (pass 2 reads) and ymem / io (writes). xmem, w2 and w3 are unused. The pointer arguments are the float_top ones; offsets are word indices in `Params`. No register and no port is added.
- **As a sequencer mode.** `case OP_SOFTMAX: st = smx::decode(rec, p); if (!st) smx::softmax_core(w0, w1, ymem, p);`. Return `ME_DIMS` / `ME_ALIGN` for status 1 / 2.
- **Legacy register mode.** `softmax_top.cpp`'s `M = 0x5F000040, K = record word` protocol. A legacy GEMM's M (at most M_MAX) never has bits [31:24] set, and the sequencer uses M[31:24] = 0xA5, so the selector collides with neither. A bare `M = 0x40` would collide with a GEMM of 64 output channels. The csynth numbers above were taken with the earlier `(M & 0xFF) == 0x40` check, a one-comparator difference.
- **Sharing.** The core's datapath is not shared with the engine: it is a separate DATAFLOW region, called in place of the engine. If both live in one top, HLS keeps both and the LUTs add.
- **Contract differences to settle** (no code changes needed in this kernel):
  1. **Quantisation rule.** The sequencer's `exec_ref.py` uses the generic q-out (`s = amax / 32767`, `q = rne(p / s)`); this kernel uses `q = round(32767 * p / pmax)` with `scale = 1/sum q`. The meaning is the same (P = q * scale); the bits differ. `exec_ref.op_softmax` should call `smx_emu.kernel()`.
  2. **Score layout.** The sequencer assumes row-major FP32 scores out of the GEMM; the int16 engine writes `Y[M/32][Np][32]`. The kernel takes either one (`F_ENGINE`), but the two directories should agree.
- **Cheaper engine-layout alternative** (not implemented): compute Q K^T with K as the engine's X (tokens = keys) and Q as W (output channels = queries). Then Y is `[query blocks][keys][32 queries]`, which is exactly the P V X layout. The kernel would need no transposer, its lag would shrink from (G-1)/G item to one 32-row block, and engine-layout time would drop to about the rows-layout 35 ms.

## Unknown / not verified

- No Vivado run, so no post-route numbers (the 0.70 factor is the brief's), and no timing closure.
- No C/RTL co-simulation: csim is broken here. The host build runs the HLS source, but the DATAFLOW FIFO depths and deadlock freedom are argued (README: rq 288, mx 32), not simulated in RTL.
- DDR bandwidth for two concurrent read streams + one write stream on the KR260 is unknown, as is the per-call overhead of the sequencer.
- The policy check uses FP32 P.V. The int16 P.V with this kernel's q and scale is the attention kernel's check (`fpga/kernels/attention`, variant `int16_smx`).
- The FP32-output build (`SMX_FP32_OUT=1`) misses the HLS budget by 0.29 ns at 4.0 ns. Its critical path is the same pass1 running-max recurrence (32-bit compare + 2 muxes) that the default build meets with 0.00 ns slack. That path is the one to watch in Vivado. If it fails there, split the max into two interleaved partial maxima.
- `build/prev_crash/` holds the pre-crash sources and results (old arithmetic, row FIFO). `build/v2_rowfifo/` holds the intermediate tested row-FIFO version.
